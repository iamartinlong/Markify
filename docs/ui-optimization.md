# UI 优化方案（调研与设计，未实施）

> 状态：**仅方案，代码未改动**。本文给出问题清单、实测数据、优化方向与分阶段实施计划。
>
> 结论先行：当前 UI「简陋」不是审美问题，而是**缺少设计令牌层**导致的三个具体后果——
> 主题切换有三处视觉断裂、层次全靠边框、交互反馈覆盖不齐。根因单一，因此可以分三期逐步收敛，
> 每期都能独立验证、独立发布，不需要一次性重写界面。

---

## 1. 怎么读这份文档

- **§2** 是实测出来的问题清单（每条都带可复现的判据与数值），决定"改什么"。
- **§3** 是方向选择，说明为什么走"令牌化"而不是"换主题库"或"重写界面"。

- **§6** 明确**不建议做的事**，避免后来者重复评估。

## 2. 现状问题（实测）

测量方式：Release 构建，`1290×850` 与 `656×500`（接近 `MinWidth=640`）两种尺寸截图，逐像素采样；对比度按 WCAG 2.1 公式计算。

### 2.1 深色主题存在三处视觉断裂

这是最明显的问题，一眼可见。

| 位置 | 实测色值 | 问题 |
| --- | --- | --- |
| 标题栏（非客户区） | `#FFFFFF` | 深色模式下仍是纯白，与窗口内容形成硬切换 |
| 菜单栏 | `#000000` | 纯黑，与其余 chrome 的 `#252526` 明显割裂 |
| 工具栏 / 标签栏 / 状态栏 | `#252526` | 基准色 |
| 编辑器 | `#1E1E1E` | 与 chrome 相差 0.008 相对亮度，几乎看不出边界 |
| 预览区 | `#0D1117` | 比编辑器更暗，同一窗口内出现第三种深色 |

**根因**：`MainWindow.axaml` 从未设置 `Window.Background`。Avalonia 用 `Background` 绘制窗口内容区的底色，`Menu` 自身不带背景，于是露出下层的窗口底色——深浅主题下这个值不一样（浅色恰好是白，所以浅色主题看不出问题）。菜单栏变纯黑是 `FluentTheme` 对无背景 `Menu` 的默认行为。

同理，标题栏是**非客户区**，由操作系统绘制，Avalonia 不控制。要统一必须显式启用扩展客户区（见 §5 第三期）。

### 2.2 编辑器与预览没有"同一张纸"的感觉

| 主题 | 编辑器 | 预览 | 相邻对比 |
| --- | --- | --- | --- |
| 浅色 | `#FFFFFF` | `#FFFFFF` | 1.00:1（完全一致，靠 1px 分隔条区分） |
| 深色 | `#1E1E1E` | `#0D1117` | 1.14:1（能看出不同，但没有理由不同） |

深色下两个面板的底色**没有设计意图**：编辑器用了 VS Code 的 `#1E1E1E`，预览用了 GitHub Dark 的 `#0D1117`。两者来自不同设计体系，拼在一起显得"不是一个应用"。

### 2.3 主题资源只有 5 个键，层次全靠边框线

`App.axaml` 里只有 5 个语义色键：

```
EditorBackground  EditorForeground  ChromeBackground  ChromeBorder  PreviewBackground
```

缺失的部分：**没有层级色**（工具栏 / 侧栏 / 状态栏只能用同一个 chrome 底色）、**没有次级文字色**（只能用 `Opacity` 压）、**没有强调色 / 危险色 / 悬停色**。

于是出现了这些替代方案：

- 次要信息靠 `Opacity="0.55"` ~ `0.7` 压低（共 5 处）。
- 分隔靠 1px 边框线（`ChromeBorder` 出现在 6 处）。
- 唯一的悬停反馈是一个硬编码的 `#40FF0000`（`App.axaml` L107）。

### 2.4 用 `Opacity` 代替次级文字色，浅色主题下有 2 处不达标

`Opacity` 是把前景色与背景混合，效果依赖背景色，所以深浅主题的表现不一致：

| 元素 | Opacity | 浅色实际色 | 对比度 | 深色实际色 | 对比度 |
| --- | --- | --- | --- | --- | --- |
| 侧栏文件路径 | 0.60 | `#75787C` | 4.17:1 ⚠ | `#8E8E8E` | 4.67:1 ✓ |
| 「尚未打开文件夹」 | 0.55 | `#808387` | 3.58:1 ✗ | `#858586` | 4.15:1 ✗ |
| 非活动标签标题 | 0.70 | `#606367` | 5.67:1 ✓ | `#9F9FA0` | 5.79:1 ✓ |
| 侧栏页签（非活动） | 0.65 | `#6A6E72` | 4.83:1 ✓ | `#979797` | 5.24:1 ✓ |
| 标签关闭按钮 ✕ | 0.50 | `#8B8E91` | 3.09:1 ✗ | `#7D7D7D` | 3.72:1 ✗ |

（WCAG AA 正文要求 4.5:1，大字/图形要求 3:1。✗ 表示连图形标准都不满足。）

**同一个 `Opacity` 在两种主题下算出不同对比度**——这正是"应该用显式次级色"的原因。改用固定色值后，两种主题可以各自调到刚好达标。

### 2.5 交互状态覆盖不全

`App.axaml` 里 12 条自定义 `Style`，只有 **1 条**定义了交互态：

```
Border.tab Button.tab-close:pointerover   ← 唯一的悬停样式
```

缺失的：

- **工具栏 11 个按钮**（新建/打开/保存/加粗/斜体/链接/代码/预览/大纲/换行/深色）全是纯文字，无图标、无悬停态、无按下态。其中 4 个是 `ToggleButton`，选中态只靠 Fluent 默认的蓝底——与主题强调色体系无关。
- **侧栏页签**（文件/大纲）用 `Opacity` 区分活动态，没有下划线或背景块，选中感很弱。
- **目录树行**无悬停态、无当前文件高亮。打开多个文件后无法从树里看出哪个是当前文档。
- **大纲列表**有 `SelectedItem` 绑定，但无自定义选中样式，依赖 Fluent 默认。

### 2.6 图标语言不统一

| 元素 | 图标 | 体系 |
| --- | --- | --- |
| 目录树文件夹/文件 | 📁 / 📄 | 彩色 emoji（U+1F4C1 / U+1F4C4） |
| 侧栏打开文件夹 | 📂 | 彩色 emoji（U+1F4C2） |
| 标签关闭 | ✕ | 几何符号（U+2715），跟随文本色 |
| 工具栏全部按钮 | 无图标，纯中文 | — |

彩色 emoji 由系统字体渲染，**字重、大小、基线都不可控**，与 Fluent 的线性图标风格冲突；且 emoji 在部分系统字体缺失时退化成方块。原代码注释里写了"用字符而非图片资源以避免加载开销"——这个判断本身合理，但选彩色 emoji 是代价。

### 2.7 间距与字号没有刻度

全项目只有 3 个字号（`14` / `12` / `11`）和 3 个 padding 值（`8,6` / `8,0,0,0` / `24,16,0,16`），margin 有 6 种互不相关的值（`4,2` / `12,8` / `12,2,12,6` / `6,4,6,0` / `8,8,8,4` / 动态缩进）。

不是"值太多"，而是**没有 4px 或 8px 的基准刻度**，导致：

- 工具栏 `Padding="8,6"`，状态栏 `Padding="12,4"`，标签栏 `Margin="6,4,6,0"`——三个横条的内边距各不相同，视觉上不齐。
- 侧栏固定 `Width="220"`，不可拖动、不记忆，且 `MinWidth=640` 时侧栏占 34%。

### 2.8 已排除的两个"疑似问题"

实测后确认**不是问题**，记录在此避免后来者重复怀疑：

| 疑似 | 实测结论 |
| --- | --- |
| 窄窗口下工具栏被裁切 | **否**。`656px` 宽时工具栏内容结束于 `x=611`，右侧余 45px，11 个按钮完整显示 |
| 窄窗口下状态栏被裁切 | **否**。`656px` 宽时状态栏完整显示「行1,列1 字数296 字符843 UTF-8」 |

（这两条最初被我误判为缺陷，逐像素测量后推翻。宽度不是问题——工具栏在 `MinWidth=640` 下仍有余量，因为按钮都是短中文标签。若将来加英文标签或图标+文字混排，才需要重新评估。）

## 3. 优化方向

### 3.1 三条可选路线

| 路线 | 做法 | 成本 | 评价 |
| --- | --- | --- | --- |
| **A. 令牌化（推荐）** | 补全设计令牌层，用令牌重写现有样式；保留现有布局 | 2–3 天 | 不改信息架构，风险最低；解决 §2 的 1/3/4/5 项 |
| B. 换主题库 | 引入第三方 Avalonia 主题包（如 Semi/Avalonia.Themes.*） | 1 天 | 能快速变好看，但 MarkView 的 Markdown 样式不在其管辖内，会与预览区风格割裂；且增加 AOT 风险 |
| C. 重写界面 | 换布局范式（如现代化 IDE 式的可折叠面板、命令面板） | 1–2 周 | 收益最大但风险最高，且与"轻量"定位冲突 |

**选 A**，理由：

1. **根因单一**。§2 的 7 个问题里有 5 个直接源于"没有令牌层"。补上令牌，问题自然消失，不需要逐个打补丁。
2. **不动信息架构**。当前布局（菜单 + 工具栏 + 标签 + 三栏）是合理的，问题在表达而非结构。重写界面等于为一个表达问题付结构代价。
3. **AOT 安全**。纯 XAML + 资源字典，不引入新依赖，不触碰反射路径。这是本项目最硬的约束（见 `todo.md` 关键约束 3）。
4. **可增量**。三期各自能独立发布，任何一期效果不满意都可以停下。

### 3.2 令牌化的核心思路

把"颜色/字号/间距"从**视图里的字面量**提升为**主题字典里的语义键**：

```
现在：  Padding="8,6"          Background="{DynamicResource ChromeBackground}"
        Opacity="0.6"          Background="#40FF0000"

之后：  Padding="{DynamicResource Space.MD}"
        Foreground="{DynamicResource Text.Secondary}"
        Background="{DynamicResource State.Hover}"
```

关键点是**语义化命名**而非"颜色命名"：`Text.Secondary` 而不是 `Gray600`。这样切换主题时只需换另一套值，视图不用动。

`MarkView` 的 Markdown 样式不在我们控制内（`GitHubTheme.axaml` 是包内资源），所以预览区的**排版**不纳入令牌化范围，只统一其**容器背景**。

## 4. 设计令牌方案（实测达标）

> **注意（2026-10-28 更新）**：风格选型已决定「VS Code 骨架 + Markify 强调色」，
> 因此底色体系改用 VS Code 2026 的官方值，本节自创的底色取值**已被取代**。
> **最新定稿令牌见 [vscode-style-discussion.md](vscode-style-discussion.md) §7**。
>
> 本节保留的价值：对比度计算方法、三档背景的思路、以及"达标"的判据仍适用。
> 若只想看最终要抄进代码的值，直接跳去那份文档。

以下取值经 WCAG 2.1 计算验证，**明暗两套主题的全部文本组合均 ≥ 4.5:1**。

### 4.1 颜色

| 语义键 | Light | Dark | 用途 |
| --- | --- | --- | --- |
| `Surface` | `#FFFFFF` | `#161B22` | 主内容面（编辑器 / 预览） |
| `Surface.Chrome` | `#F3F5F7` | `#1C222A` | 工具栏 / 标签栏 / 状态栏 |
| `Surface.Sunken` | `#EBEEF1` | `#12171D` | 侧栏（下沉一档，形成层次） |
| `Border` | `#D5DBE1` | `#2C3540` | 常规分隔线 |
| `Text.Primary` | `#1B1F24` | `#E4E8ED` | 正文 |
| `Text.Secondary` | `#4E5964` | `#A9B4BF` | 次级信息（替代 `Opacity 0.7`） |
| `Text.Tertiary` | `#636D79` | `#7E8A96` | 弱提示（替代 `Opacity 0.55`） |
| `Accent` | `#2166D8` | `#4A85F3` | 强调色（选中、链接） |
| `Accent.Foreground` | `#FFFFFF` | `#0B1017` | 强调色上的文字 |
| `Danger` | `#C1352B` | `#F08A80` | 危险操作（关闭按钮悬停） |

**对比度实测**（三档背景 × 四档前景，取最差值）：

| 前景 | Light 最差 | Dark 最差 |
| --- | --- | --- |
| `Text.Primary` | 14.22:1 | 13.01:1 |
| `Text.Secondary` | 6.14:1 | 7.60:1 |
| `Text.Tertiary` | 4.51:1 | 4.55:1 |
| `Accent` | 4.56:1 | 4.53:1 |

三档背景之间的相邻对比在 `1.04`–`1.17` 之间——足以辨识层次，又不至于像"色块拼接"。

### 4.2 间距刻度（4px 基准）

| 键 | 值 | 用途 |
| --- | --- | --- |
| `Space.XS` | `4` | 图标与文字间距 |
| `Space.SM` | `8` | 控件内边距 |
| `Space.MD` | `12` | 分组间距 |
| `Space.LG` | `16` | 区块间距 |
| `Space.XL` | `24` | 内容区留白 |

统一后：菜单/工具栏/标签栏/状态栏的上下内边距都用 `Space.SM`（8px），不再出现 `6` / `4` 混用。

### 4.3 字号刻度

| 键 | 值 | 用途 |
| --- | --- | --- |
| `Font.Caption` | `11` | 状态栏、路径提示 |
| `Font.Body` | `12` | 标签、侧栏、按钮 |
| `Font.Code` | `14` | 编辑器 |

保持现状（3 档够用），只是给它命名。**不建议**引入更多档位——轻量工具不需要 7 级字号体系。

### 4.4 圆角与状态

| 键 | 值 |
| --- | --- |
| `Radius.SM` | `4` |
| `Radius.MD` | `6` |
| `State.Hover` | Light `#0A000000` / Dark `#0AFFFFFF`（8% 叠加，随主题自动反转） |
| `State.Pressed` | Light `#14000000` / Dark `#14FFFFFF` |
| `State.Selected` | Light `#E3EEFB` / Dark `#1F3A5F` |

`State.Hover` 用"半透明黑/白"而不是固定色值，这样同一个令牌能同时适配三档背景——这是 Fluent 的做法，也是 `#40FF0000` 应该被替换成的东西。

## 5. 分三期实施

### 第一期：修断裂 + 建令牌（约 1 天）

**目标**：让深浅主题各自内部一致。这是用户感知最强、风险最低的一期。

> **色值以 [vscode-style-discussion.md](vscode-style-discussion.md) §7 的定稿令牌为准**
> （VS Code 骨架 + Markify 强调色），不是本节上方 §4 的自创值。

| 改动 | 落点 |
| --- | --- |
| 设置 `Window.Background`，修复菜单栏纯黑 | `MainWindow.axaml` 加 `Background="{DynamicResource Surface.Chrome}"` |
| 建立令牌字典（§4 全部键） | `App.axaml` 的 `ThemeDictionaries` 从 5 键扩到 ~20 键 |
| 用令牌替换所有 `Opacity` 文本压暗 | 5 处 `Opacity` → `Text.Secondary` / `Text.Tertiary` |
| 用 `State.Hover` 替换 `#40FF0000` | `App.axaml` L107 |
| 统一 chrome 内边距为 `Space.SM` | 菜单/工具栏/标签栏/状态栏 |
| 统一编辑器与预览的底色（同用 `Surface`） | 消除 `#1E1E1E` 与 `#0D1117` 的两套深色 |

**验证**：
- 逐像素采样 8 个区域，确认深色下无 `#FFFFFF` / `#000000` 残留。
- 用 §2.4 的对比度脚本跑一遍，确认全部 ≥ 4.5:1。
- 浅色主题回归：确认没有把浅色改坏（改动前先截一份基线）。

**风险**：低。纯资源与样式改动，不碰逻辑。唯一注意点是 `MarkView` 的预览容器背景要跟着令牌走，但**不要动它内部的 Markdown 样式**。

### 第二期：交互反馈与图标（约 1–1.5 天）

**目标**：解决"点了没反应"的观感，统一图标语言。

| 改动 | 说明 |
| --- | --- |
| 工具栏按钮加悬停/按下态 | 用 `State.Hover` / `State.Pressed` |
| 工具栏加图标 | 用**几何符号或内置 Path**（如 `M8 2v12` SVG path），**不引入图标字体包**（AOT 与体积风险） |
| `ToggleButton` 选中态改用 `Accent` | 替换 Fluent 默认蓝 |
| 侧栏页签加活动指示（下划线或背景块） | 当前只靠 `Opacity`，选中感弱 |
| 目录树行加悬停态 + 当前文件高亮 | 需要 VM 暴露"当前文档路径"，与文件树节点比对 |
| 目录树图标换成单色几何符号 | `📁` → `▸`/`▪` 或 Path 图标；**去掉彩色 emoji** |

**图标方案的取舍**：项目已有 `Avalonia.Fonts.Inter` 依赖，但没有图标字体。可选：

1. **内置 `Path` 几何**（推荐）— 零依赖、AOT 安全、可精确控制大小与颜色。缺点是每个图标要手写 path 数据（约 20 个图标，可从 Material Symbols 抄 MIT 授权的 path）。
2. 引图标字体（如 `FluentIcons`）— 省事，但增加约 200KB 字体且需验证 AOT。
3. 保持纯文字 — 最省事，但"简陋"的观感主要来源之一。

选 1。**不要用彩色 emoji**。

**验证**：UI 自动化用 `SendInput` 移动鼠标到各按钮截图对比（注意 pitfalls F9/F10 的教训：验证要看状态栏或日志，不要依赖剪贴板）。

### 第三期：结构与打磨（约 1–2 天，可选）

按优先级：

| 项 | 说明 | 价值 |
| --- | --- | --- |
| 标题栏统一 | 启用 `ExtendClientAreaToDecorationsHint`，让标题栏跟随主题 | 高（深色下白标题栏很刺眼），但需处理窗口拖动/最大化按钮 |
| 侧栏可拖动 + 记忆宽度 | 现在固定 220px | 中 |
| 空状态设计 | 「尚未打开文件夹」现在是一行灰字 | 中 |
| 标签栏溢出处理 | 现在只有水平滚动，无下拉列表 | 中（标签多时难找） |
| 状态栏分区 | 现在是一行平铺，可加分隔符与图标 | 低 |

**标题栏的风险**：`ExtendClientAreaToDecorationsHint` 会接管非客户区，需要自己实现窗口按钮与拖动区域，**可能影响 `--selftest` 的窗口截图断言**。建议单独一期验证，且在 AOT 下重跑自检。

## 6. 不建议做的事

| 方案 | 为什么不建议 |
| --- | --- |
| 引入完整 UI 组件库（如 FluentAvalonia） | 与现有 FluentTheme 重叠，且增加 AOT 验证面；收益仅是控件外观，解决不了"没有令牌层"的根因 |
| 上 WebView 渲染界面 | 违背项目核心约束（轻量、无 WebView），见 README 技术选型 |
| 重写为 WYSIWYG | 已在 `todo.md` P3-2 评估过，等于写一个 Markdown 感知的富文本编辑器，成本远超收益 |
| 为预览区单独做一套主题 | MarkView 的样式在包内，强行覆盖会在升级时全部失效；只统一容器背景即可 |
| 追求"像素级对齐某款主流编辑器" | 目标是"看起来是同一个应用"，不是"看起来像 VS Code"。后者会把轻量工具拖成模仿品 |
| 一次改完三期 | 每期都有可感知的收益，分批发布能让问题暴露在最小改动上 |

## 8. 立即可做的第一步

如果只做一件事：**在第一期动手前，先截一套基线图**（浅色/深色 × 宽/窄，共 4 张），存到 `docs/ui-baseline/`。

理由：UI 改动最大的风险是"改好了 A 却弄坏了 B"，而这类回归**没有测试能挡住**（项目无 UI 自动化测试，见 `todo.md` 技术债）。有了基线图，至少能靠肉眼快速比对。

本文 §2 的所有数值都可以用同样的方式复测——脚本思路是：截图 → 逐像素采样 → 与期望值比对。不需要引入视觉回归框架。
