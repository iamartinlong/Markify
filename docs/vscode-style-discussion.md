# 是否做成 VS Code 风格：讨论与决策

> 状态：**讨论稿，未实施**。本文不写"怎么做"（那在 [ui-optimization.md](ui-optimization.md)），
> 而是回答"**要不要**做成 VS Code 风格、做到哪一层、代价是什么"。
>
> 结论先行：**建议"抄原则，不抄外形"**——采用 VS Code 的主题分层手法与交互约定，
> 但**不复制它的活动栏与多级 chrome**。理由见 §4：抄外形会在 640px 最小宽度下把布局挤爆。

---

## 1. 先把"VS Code 风格"拆开

这个词至少指三种不同的东西，代价相差一个数量级：

| 层 | 具体内容 | 成本 | 与 Markify 的契合度 |
| --- | --- | --- | --- |
| **L1 视觉手法** | 两层底色 + 1px 边框分区、半透明悬停、活动标签与内容同色、紧凑行高 | 约 1 天 | **高**。纯主题层，不动结构 |
| **L2 交互约定** | 活动栏、命令面板（`Ctrl+Shift+P`）、面包屑、状态栏分区、侧栏可折叠 | 约 2–3 天 | **中**。部分契合，部分与"轻量"冲突 |
| **L3 布局范式** | 活动栏常驻 + 可拖动侧栏 + 底部面板 + 编辑器组（分组/拆分） | 约 1–2 周 | **低**。为一个 Markdown 工具复制 IDE 的复杂度 |

多数人说"VS Code 风格"时，指的实际是 **L1 + 一点 L2**（看起来像、用起来顺手），而不是 L3。

---

## 2. L1：视觉手法——这才是"像 VS Code"的真正来源

我从本机 VS Code 安装目录读出了官方 2026 主题的真实取值（`theme-defaults/themes/2026-dark.json`，333 个颜色键），不是凭记忆。

### 2.1 VS Code 的核心手法：整体一片，靠细线分区

| 层 | Dark | Light | 说明 |
| --- | --- | --- | --- |
| chrome（标题栏/活动栏/侧栏/状态栏/标签栏背景） | `#191A1B` | `#FAFAFD` | **全部同一个色** |
| 内容（编辑器） | `#121314` | `#FFFFFF` | 与 chrome 只差一点点 |
| 活动标签 | `#121314` | `#FFFFFF` | **与编辑器完全同色** |

关键数字：

- chrome 与内容层的对比只有 **1.067:1（Dark）/ 1.042:1（Light）**——几乎看不出来。
- 分界靠 1px 边框，对比 **1.23–1.31:1**。
- 活动标签与编辑器**同色**，视觉上"标签是编辑器的一部分"，没有接缝。

**这与 Markify 现状方向相反**：Markify 把编辑器设成 `#1E1E1E`、预览设成 `#0D1117`，两个**不同的深色**——等于用"面之间硬拉色差"来分区。这是 §2 里"看起来不是一个应用"的根因。

### 2.2 半透明叠加：一个颜色适配所有底色

VS Code 的悬停/选中不用固定色值：

```
Dark   list.hoverBackground  #FFFFFF14   （8% 白）
Light  list.hoverBackground  #00000014   （8% 黑）
```

叠加后与底色的对比约 1.20–1.25:1，刚好够看出"鼠标在这"，又不刺眼。**同一个键值可以套在三层底色上都不用改**。

这正是 Markify 的 `#40FF0000`（纯红 25%）应该被替换成的东西——后者是硬编码，深色下叠加成 `#5C1C1C`，几乎看不出。

### 2.3 VS Code 自己的对比度是达标的

我算了它 10 组关键文本的对比度，**全部 ≥ 4.5:1**：

| 项 | Dark | Light |
| --- | --- | --- |
| 侧栏文字 | 9.48:1 | 15.64:1 |
| 非活动标签 | 5.18:1 | 6.04:1 |
| 状态栏文字 | 5.18:1 | 6.04:1 |
| 行号 | 5.21:1 | 6.29:1 |
| 按钮文字 | 4.79:1 | 5.39:1 |

**这意味着 L1 可以直接抄它的色值**，不需要我再自创一套——我已经在 `ui-optimization.md` §4 自创了一套（也达标），但抄官方值有个额外好处：**用户若同时用 VS Code，两个应用的观感一致**。

### 2.4 L1 的判定：值得做

| 项 | 评价 |
| --- | --- |
| 风险 | 低。纯 `App.axaml` 资源与样式，不碰逻辑 |
| AOT | 无影响 |
| 工作量 | 约 1 天（与 `ui-optimization.md` 第一期基本重合，只是色值来源从"自创"改为"抄官方"） |
| 收益 | 高。"简陋"的观感主要来自此层 |

**建议**：把 `ui-optimization.md` §4 的自创令牌**换成 VS Code 2026 的真实值**，其余不动。这样第一期的工作量不变，但结果更"眼熟"。

## 3. L2：交互约定——要挑着抄

### 3.1 值得抄：命令面板（`Ctrl+Shift+P`）

Markify 已有 **31 个 `[RelayCommand]`**，但分散在菜单（文件/编辑/视图）、工具栏、标签右键菜单三处。用户要找一个命令得先猜它在哪。

命令面板只需一个 `Popup` + 一个 `TextBox` + 一个过滤后的 `ListBox`，数据源直接复用现有命令。这是**L2 里投入产出比最高的一项**。

代价也很实际：

- 需要给 31 个命令补中文显示名与分类（现在多数是方法名，没有面向用户的标签）。
- 需要一套键盘导航（上下选择、回车执行、Esc 关闭）。
- 约 1 天。

### 3.2 值得抄：活动标签与内容同色（L1 已覆盖）+ 标签栏紧凑

VS Code 的标签栏只有 35px 高，标签之间没有间距、没有圆角，靠背景色差区分活动态。Markify 现在是圆角 `4,4,0,0` + 间距 + 半透明，观感更"卡片化"。

改成方形、无间距、同色融合，视觉上立刻"像"了。成本接近零（几行样式）。

**但有个副作用**：Markify 的标签关闭按钮 `✕` 是常显的，VS Code 是悬停才显示未保存圆点。方形无间距后，常显的 `✕` 会显得拥挤。要么改成悬停显示，要么保留间距。

### 3.3 谨慎抄：活动栏（最左侧图标列）

这是 **L2 里最诱人也最危险的一项**。我算了空间账：

| 方案 | 侧栏总占宽 | 640px 窗口下剩余 | 每栏宽度 |
| --- | --- | --- | --- |
| 现状（仅侧栏 220px） | 220px（34%） | 420px | 210px ✓ |
| VS Code 风格（活动栏 48 + 侧栏 240） | 288px（45%） | 352px | 176px ✗ |

**关键约束**：`MainWindow.axaml` 里编辑与预览各 `MinWidth="200"`。

```
288（活动栏+侧栏） + 200 + 1（分隔条） + 200 = 689 > 640（MinWidth）
```

**加活动栏会让布局在最小宽度下挤爆**。要么把 `MinWidth` 提到 700，要么在窄窗口下自动收起侧栏，要么放弃活动栏。

而且 Markify 的侧栏只有**两个页签**（文件/大纲），活动栏为两个图标占 48px 常驻宽度，性价比很低——VS Code 的活动栏能放 5–8 个视图，才有存在意义。

**建议**：**不做活动栏**。改用侧栏顶部的页签（已经有了），或升级为图标+文字的紧凑分段控件。

### 3.4 谨慎抄：面包屑

Markify 是"打开文件夹 + 多文件"模型，面包屑能显示当前文件在目录中的位置。但侧栏的文件树已经承担了这个职责，且面包屑要占一行（约 28px）。

**建议**：先不做。若将来侧栏经常被收起，再加。

### 3.5 可以抄：状态栏分区与紧凑

VS Code 的状态栏把信息分区，每区可点击。Markify 现在是平铺的 5 段文字。

改成"可点击的分区"（如点击编码名 → 切换编码，点击字数 → 无操作），成本低但需要对应功能存在。**建议只做视觉分区（加分隔符），不做交互**——避免出现"点了没反应"的分区。

## 4. L3：布局范式——不建议

| 项 | 为什么不建议 |
| --- | --- |
| 编辑器组（可拆分多个组） | Markify 已用"单编辑器 + 切换 TextDocument"省开销（见 `todo.md` 关键约束 2）。做编辑器组等于推翻这个决策，TextMate 开销会成倍增长 |
| 底部面板（终端/输出/问题） | 没有终端可放。为"像 VS Code"造一个空面板是纯负担 |
| 可拖动 + 可折叠的完整侧栏系统 | 收益是空间管理，但 Markify 的侧栏只有两个视图，复杂度不划算 |
| 命令面板之外的所有快捷键体系 | VS Code 有 200+ 快捷键。Markify 已有 14 个，覆盖了核心操作 |

**核心判断**：VS Code 是**通用代码编辑器**，它的复杂度来自"支持任意语言、任意项目、任意工作流"。Markify 是**单一用途的 Markdown 工具**。抄 L3 等于为一个明确用途付通用工具的代价。

## 5. 垂直空间的账

VS Code 风格的一个直接好处是"内容区更大"。实测截图的像素带：

| 方案 | 菜单栏 | 工具栏 | 标签栏 | 合计 |
| --- | --- | --- | --- | --- |
| Markify 现状 | 32px | 43px | 34px | **109px** |
| VS Code 风格（取消菜单+工具栏） | — | — | 35px（+标题栏 35px） | **70px** |

省 **39px**，在 820px 高的窗口里相当于内容区 +5.5%。

**但代价是**：取消工具栏意味着 11 个按钮的功能只能从菜单或命令面板进入。对于"加粗/斜体/链接/代码"这类**高频格式操作**，多一层点击是明显的退步。

**折中方案（推荐）**：

1. **保留工具栏，但瘦身**——只留格式按钮（加粗/斜体/链接/代码）+ 预览切换，把"新建/打开/保存"移到菜单（它们有快捷键，工具栏上是冗余的）。可省约 20px 宽度，高度不变。
2. **菜单栏合并进标题栏**（VS Code 的 `menuBar.visibility: toggle` 模式）——需要 `ExtendClientAreaToDecorationsHint`，属于第三期的风险项。
3. 若确实要极致紧凑，提供"专注模式"（隐藏工具栏与状态栏，`F11` 式切换），而不是默认取消。

## 6. 决策建议

### 6.1 推荐路线：抄原则，不抄外形

| 项 | 决策 | 理由 |
| --- | --- | --- |
| L1 视觉手法 | **做**（约 1 天） | 收益最高、风险最低；"简陋"的主因在此 |
| L2 命令面板 | **做**（约 1 天） | 31 个命令已有，缺入口 |
| L2 标签栏紧凑化 | **做**（约 0.5 天） | 几行样式，观感提升明显 |
| L2 活动栏 | **不做** | 2 个视图占 48px 常驻宽度不值；会把 640px 布局挤爆 |
| L2 面包屑 | **暂不做** | 文件树已覆盖该职责 |
| L3 布局范式 | **不做** | 与"轻量"定位和现有架构决策冲突 |

合计 **约 2.5 天**，分两期发布（视觉 / 交互），每期可独立回退。

**2026-10-28 已确认此路线**，详见 §7 的决定与定稿令牌。

### 6.2 色值来源的取舍

两个选项，都达标：

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| A. 抄 VS Code 2026 官方值 | 与用户日常环境一致；经过大规模验证 | 是"模仿"，缺乏自身识别度；VS Code 主题会随版本变 |
| B. 用 `ui-optimization.md` §4 的自创值 | 有独立观感；值固定可控 | 需要自己保证长期一致 |

**建议选 A 的骨架 + B 的强调色**：底色体系抄 VS Code（`#191A1B` / `#121314` / `#FAFAFD` / `#FFFFFF`），强调色保留 Markify 自己的 `#2166D8` / `#4A85F3`。这样既"眼熟"又不完全是人家的复制品。

### 6.3 一个必须承认的限制

Markify 的**预览区样式不在自己手里**——`MarkView` 的 Markdown 排版来自包内的 `GitHubTheme.axaml`。所以：

- 编辑器侧（AvaloniaEdit）可以完全 VS Code 化，连 TextMate 主题都能换（现在是 `DarkPlus` / `LightPlus`，**本来就是 VS Code 的**）。
- 预览侧只能统一容器背景，Markdown 元素的字号/间距/颜色由 MarkView 决定。

结果会是"编辑器像 VS Code，预览像 GitHub"——**这恰好是 VS Code 预览 Markdown 时的实际观感**，所以不算违和，但要知道这是设计边界而非疏漏。

## 7. 决定（2026-10-28）

**已决定：前者——目标是"精致的 Markdown 工具"，不是 VS Code 插件。**

据此确定：

| 项 | 决定 |
| --- | --- |
| 色值来源 | **VS Code 2026 的骨架 + Markify 自己的强调色**（§6.2 的混合方案） |
| 底色体系 | 抄 VS Code：`#191A1B` / `#121314` / `#FAFAFD` / `#FFFFFF` |
| 强调色 | 保留自有 `#2166D8` / `#4A85F3`，不用 VS Code 的 `#0069CC` |
| 活动栏 | 不做 |
| L3 布局范式 | 不做 |
| 命令面板 | 做 |
| 图标与字体 | **不追求与 VS Code 对齐**，用内置 Path 几何图标 |

### 定稿令牌（混搭后实测复核）

| 语义键 | Light | Dark |
| --- | --- | --- |
| `Surface`（编辑器 / 预览） | `#FFFFFF` | `#121314` |
| `Surface.Chrome`（侧栏 / 状态栏 / 标签栏） | `#FAFAFD` | `#191A1B` |
| `Border` | `#E2E2E5` | `#2A2B2C` |
| `Border.Strong`（分隔条） | `#D4D4D4` | `#454545` |
| `Text.Primary` | `#202020` | `#BFBFBF` |
| `Text.Secondary` | `#606060` | `#8C8C8C` |
| `Accent` | `#2166D8` | `#4A85F3` |
| `Accent.Foreground` | `#FFFFFF` | `#0B1017` |
| `Danger` | `#C1352B` | `#F08A80` |
| `State.Hover` | `#00000014` | `#FFFFFF14` |
| `State.Pressed` | `#00000024` | `#FFFFFF24` |
| `State.Selected` | `#2166D834` | `#4A85F31C` |

复核结果：

- 纯底色上最差文本对比：Light **5.09:1**、Dark **4.93:1**（均 ≥ 4.5:1）
- 悬停 / 按下 / 选中态上的 `Text.Primary` 最差：Light **11.34:1**、Dark **6.20:1**
- 选中态可辨识度（与未选中底相比）：Light **1.328:1**、Dark **1.146:1**（均 > 1.12，看得出选中）

### 调参过程中发现的一条规则

混搭时踩到一个坑，值得单独记：**次级文字不能用在交互行上**。

约束是冲突的：

| 要求 | 需要的 alpha |
| --- | --- |
| 悬停/按下"看得出来" | ≥ 8–10% |
| `Text.Secondary` 在叠加后仍 ≥ 4.5:1 | 只能 4–6% |

深色主题下按下态若用 `0x24`（14%），`Text.Secondary` 掉到 **3.34:1**——不达标。

**解法不是调 alpha，而是改规则**：

- 交互行（文件树行、列表项、标签）上的文字用 `Text.Primary`
- `Text.Secondary` 只用于**非交互**的说明文字（路径提示、状态栏、占位提示）

这样 alpha 可以放心放到 8–15%，选中感明显，且 `Text.Primary` 对比度余量充足。VS Code 也是这么做的——它的 `sideBar.foreground`（`#BFBFBF`）本身就是主文字级，不靠压暗表示次要。

### 对 `ui-optimization.md` 的影响

该文档 §4 自创的令牌值**被本节取代**——底色改用 VS Code 骨架，强调色保留。§5 的三期计划不变，只是第一期的色值来源改为本节表格。

## 8. 实施约束（据此决定）

| 约束 | 说明 |
| --- | --- |
| 预览区只改容器 | `MarkView` 包内的 `GitHubTheme.axaml` 不动，否则升级即失效 |

## 9. 附：本文数据的复现方式

所有 VS Code 色值来自本机安装目录，可直接核对：

```
D:\soft\Microsoft VS Code\<build>\resources\app\extensions\theme-defaults\themes\
  ├── 2026-dark.json      333 键（含 include: dark_modern → dark_plus → dark_vs）
  ├── 2026-light.json     347 键
  ├── dark_plus.json       36 键（覆盖项）
  └── light_plus.json      41 键
```

注意 `dark_plus.json` 只有 36 个键——它是覆盖层，完整值要顺着 `include` 链合并。**只读它一个文件会得出错误结论**（我第一次就读错了，以为 VS Code 侧栏是 `#252526`）。

对比度按 WCAG 2.1 公式计算，半透明色先按 alpha 合成到背景再算。
