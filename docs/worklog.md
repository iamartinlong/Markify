## v0.5.1 — 交接文档与一个静默丢修改的缺陷（2026-10-28）

**目标**：写交接文档（`todo.md` / `worklog.md`），给接手者一个可执行的起点。纯修复版，无新功能。

### 写文档时发现的缺陷

核对数据时注意到**有一次测试失败但无法复现**。这类"偶发失败"会训练人养成"重跑到绿为止"的习惯，进而掩盖真正的间歇性缺陷，所以没有跳过。

**问题 1：5 个测试时序不稳定（F11）**

`FileChangeWatcherTests` 用固定 `Task.Delay(150)` 等 `FileSystemWatcher` 就绪、`Task.Delay(1500)` 等防抖窗口。负载高时事件还在路上，断言就提前执行。改为"轮询到条件成立 + 超时"。

**问题 2：一个会静默丢失修改的产品缺陷（F12 → F13）**

修完时序后，"抑制自身写入"的测试暴露了真问题。原实现是：

```csharp
_owner._ownWriteInProgress = true;                                    // 抑制开始
_ = Task.Delay(500).ContinueWith(_ => _ownWriteInProgress = false);   // 延迟解除
```

这 500ms 内**所有**文件事件都被当作"自己写的"丢弃。真实场景——保存后立刻被 git 或格式化工具修改——那次修改被静默忽略，用户以为文件是最新的。

改为时间戳窗口：仍保留 500ms 宽限，但语义从"这段时间内一律忽略"变成"只忽略紧挨着自身写入的事件"。

### 一个值得记住的测试原则

**这个问题是被"正向对照"逼出来的**：原测试只断言"抑制期间 0 个事件"，而 watcher 完全坏掉时这条也是绿的。加上"先证明能检测到探测写入、再证明宽限期后能恢复"之后，缺陷立刻暴露。

> 凡是断言"不发生 X"的测试，都要先证明"正常条件下 X 会发生"。否则它只能证明代码没抛异常。

### 附带修复的测试代码 bug

`EnsureWatchingAsync(watcher, path, 0)` 传了字面量 `0`，函数内部轮询的是参数副本，永远看不到事件处理器对原变量的递增——导致探测阶段就必然超时。async 方法又不能加 `ref` 参数，改用 `Func<int>` 读取。

### 附带修复的文档结构损坏（v0.5.0 起）

审计时发现 `pitfalls-and-practices.md` 的一级标题跑到了第 194 行，B8/B9/F10 悬在文件最开头，F9 被夹在 H 与 I 之间。溯源确认是 **v0.5.0 提交时插入位置错误**（不是本次引入），v0.5.1 又在同一位置追加了 F11–F13，叠加成更乱的形态。

**为什么会发生**：用脚本按行号插入内容时，行号是在**另一份副本**上算的，插入点因此错位。而且这类错误不影响编译、不影响测试，肉眼读正文也看不出——只有检查文档结构才会暴露。

**修复方式**：不按行号硬插，改为按标题定位章节边界，再在边界处插入。改完后用「非空行多重集与原文完全一致」校验，确保只动了顺序、没丢内容（786 行对 786 行，差异 0）。

**教训**：文档结构也需要验证。对脚本改文档的场合，「改完比对内容集合」是成本最低的兜底——它能同时抓住"丢了内容"和"重复了内容"，这两类是手工改文档最常见的破坏。

### 验证

105 个用例**连跑 10 次全通过**（修复前约每 4 次有 1 次失败）、10 项自检（JIT + AOT）通过、0 警告。CI 与 CD 均绿。

### 遗留

- 宽限期仍是 500ms：自身保存后 500ms 内的外部修改仍会被忽略。这是有意的折中（吸收迟到的文件事件），已记入 todo 技术债。
- 该缺陷的根因是"用布尔开关表达时间区间"，同类写法在其他地方值得再排查一遍。

## v0.5.0 — 文件夹与标签增强（2026-10-28）

**目标**：用户提出三个需求——标签悬停显示路径、标签右键菜单、打开文件夹。

| 功能 | 实现要点 |
| --- | --- |
| 标签路径提示 | `TabToolTip` 属性；未保存文档显示「尚未保存，无文件路径」而非空白 |
| 标签右键菜单 | 8 项。**作用于被右键的标签**，不是当前活动标签 |
| 文件夹目录树 | 侧栏改为「文件 / 大纲」两个页签，而非堆叠 |

### 关键决策

**侧栏用页签而非堆叠**：侧栏宽度只有 220px，上下堆叠会让目录树和大纲都很挤。页签切换每个时刻只显示一个，空间利用率更好（与 VS Code 一致）。

**目录树懒加载**：只在展开时枚举子目录。一次性递归整个仓库会卡住 UI，而用户多数时候只看一两个子目录。

**目录树跳过噪音目录**：`.git`、`node_modules`、`bin`、`obj` 等不进树。单层上限 2000 条，避免误选磁盘根目录时挂起。

**单个坏目录返回空节点而非抛异常**：调用方是 UI，一次异常会让整棵树加载失败。

### 审计发现（发布前）

**1. 右键菜单完全不可用** — 最严重

初次用 `$parent[ItemsControl]` 相对绑定，但 `ContextMenu` 是弹出层、不在视觉树，绑定解析不到 → 全部灰显。改试 `PlacementTarget`，日志显示 `Opening` 时它已是 `null`。最终方案：`PointerPressed` 时记录目标。

**2. 7 个 `async void` 处理器无异常保护** — 异常会终结进程。统一包一层并写入状态栏。

**3. 死代码** — `FileTreeNode.IsSelected` 从未使用，删除。

### 验证

105 单测、10 项自检（JIT + AOT）、发布版实测右键菜单生效（状态栏显示复制路径）。

### 遗留

- 单击目录树即开标签，无"预览态"（见 todo P1-2）
- 文件夹不记忆（见 todo P1-1）

## v0.4.0 — 导出 HTML / PDF（2026-10-28）

**目标**：把文档导出为可分发、可打印的格式。

| 能力 | 实现 |
| --- | --- |
| HTML | Markdig 转 HTML + 内联 CSS + 本地图片内嵌 base64 |
| PDF | 复用 HTML 输出，交给系统 Edge/Chrome 无头打印 |

### 关键决策

**PDF 不用第三方库**：QuestPDF 等需要把 Markdown 重新排版一遍，等于维护第二套渲染器，样式会与预览、HTML 导出逐渐分叉。复用浏览器排版引擎能保证三者一致，且 Edge 在 Windows 10+ 系统自带。

**本地图片内嵌而非引用路径**：导出文件常被单独分发或归档，相对路径会失效。远程图片保留 URL（不下载、不改语义），找不到的本地图片保留原路径（静默删图比坏链接更糟）。

**不做代码高亮**：Highlight.js 需要 CDN（离线失效）或内嵌约 100KB。当前选朴素等宽样式，记入已知限制。

### 踩坑

**`<details>` 整块被丢弃**：MarkView 的 `UseHtmlDetails()` 会在 AST 生成自定义 `DetailsBlock`，但 Markdig 的 HTML 渲染器不认这个节点——`Markdown.ToHtml()` 会把整段（连标签带内容）静默丢掉。用 AST dump 才定位到。解法：解析前抽成占位符，渲染后还原。

**审计修复**：
- 保存失败时残留 `.markify-tmp`（用户文档目录会越堆越脏）
- `OpenPathAsync` 的 `Path.GetFullPath` 在 `try` 外，非法路径会从 `async void` 逃逸导致进程崩溃
- `PdfExporter` 传了 `--no-sandbox`（普通用户下无收益，纯削弱安全）
- stdout 读取任务从未 await（注释说要读走否则子进程挂死，但只处理了 stderr）
- 自检未覆盖 HTML 导出 → 补上，因为 `[GeneratedRegex]` 正是 AOT 易失效点

### 验证

82 单测、自检 10 项（含新增 `html-export`）、PDF 实测 8 页分页且中文 CIDFont 嵌入正确。

## v0.3.0 — 多标签页、查找、外部修改检测（2026-10-28）

**目标**：补三项基础能力。

| 能力 | 实现要点 |
| --- | --- |
| 多标签页 | `MainViewModel`（工作区）+ `DocumentViewModel`（文档）拆分 |
| 查找替换 | 复用 AvaloniaEdit 的 `SearchPanel` |
| 外部修改检测 | `FileChangeWatcher` 封装 `FileSystemWatcher` |

### 关键决策

**单编辑器 + 切换 `TextDocument`**，而不是每个标签建一个 `TextEditor`。每个 `TextEditor` 都要安装一套 TextMate 语法与 transformer，十几个文件时开销明显。代价是标签间共享语法高亮与查找面板状态。

**文件监听必须处理两件事**：防抖（一次保存触发多个事件）、自身写入抑制（否则应用保存时会提示"被外部修改"）。

### 踩坑

- **所有标签都叫「未命名.md」**：启动文档创建时没递增计数器
- **Ctrl+F 完全没反应**：`ApplicationCommands.Find` 从 `TextArea` 内部路由，窗口级快捷键拦不到
- **连续两次外部修改弹两个对话框**：缺重入保护
- **`dotnet test` 跑不了 xunit.v3**：.NET 10 的 `dotnet test` 对 Microsoft.Testing.Platform 集成不稳定，报「运行了 0 个测试」。改用 `dotnet run --project`

### 验证

55 单测。**做了负向验证**：故意改坏断言确认退出码为 1，确保 CI 不会因测试没跑而假通过。

## v0.2.2 — 占位 Logo（2026-10-27）

| 项 | 说明 |
| --- | --- |
| 设计 | 深靛蓝圆角方块 + 白色 M 折线 + 琥珀圆点 |
| 生成 | `tools/LogoGen` 从一份几何定义输出 SVG / PNG / ICO |

### 关键决策

**程序生成而非手绘**：三份文件（SVG/PNG/ICO）如果各自维护，改一次设计要同步导出三次，漏一次就会出现"标题栏是新图标、exe 还是旧的"。

**M 用折线而非字体**：字体字形在 16px 下会糊，且跨系统不一致。

### 发现的缺陷

**项目原本没有 `<ApplicationIcon>`**：exe 一直用 .NET 默认图标，而窗口标题栏显示 Avalonia logo，两者不一致。

CI 增加图标一致性校验（产物与生成器比对 SHA-256），并做了负向测试确认能检出。

## v0.2.1 — 界面缺陷修复（2026-10-27）

三个用户报告的视觉问题：

| 问题 | 根因 |
| --- | --- |
| 左右分栏底部 120px 空白 | Grid 行 `Height=0` 但 `MinHeight=120`，**最小高度优先级更高** |
| 预览滚动条压住表格边框 | MarkView 用 overlay 滚动条、不预留布局宽度 |
| 行号栏上下各漏 8px | 编辑器 `Padding` 连行号槽一起内缩 |

**第一条的教训**：`MinHeight` 会覆盖 `Height`，即使后者是 0。

**第二条的教训**：调**容器** padding 无效（会连滚动条一起移，相对位置不变），必须改**内容层**的 margin。判断方法：移动前后测两者相对距离，距离不变就说明动错层了。

## v0.2.0 — 安装包（2026-10-27）

| 项 | 说明 |
| --- | --- |
| 工具 | Inno Setup 6 |
| 能力 | 开始菜单项、Markdown 文件关联 |

### 为什么需要安装包

便携 zip 无法注册文件关联，而「双击 `.md` 直接打开」正是 Markdown 编辑器的核心场景。

### 踩坑

**卸载必须还原关联，不能只删除**：最初用 `uninsdeletevalue`，卸载后 `.md` 变成**空字符串**——用户原本的 VSCode 关联丢失。改为安装时备份到注册表、卸载时写回。

**验证方法也要讲究**：用「卸载后等于安装前」作判据，在值恰好相同时会静默通过。改用**哨兵值**（`Sentinel.TestHandler`）才能得到确定性证据。这是 pitfalls F8 的来源。

## v0.1.0 — 首个版本（2026-10-27）

**目标**：验证「Avalonia + 原生控件渲染 Markdown」这条路可行。

| 能力 | 说明 |
| --- | --- |
| 分栏编辑预览 | AvaloniaEdit + MarkView |
| 滚动同步 | 双向，按比例 |
| 大纲导航 | Markdig AST → 标题，GitHub 锚点规则 |
| 文件 IO | 编码/BOM 保持，原子写入 |
| 明暗主题 | 界面 / 编辑器 / 预览三者联动 |

### 技术选型结论

| 方案 | 结论 |
| --- | --- |
| **MarkView.Avalonia** | ✅ 采用：MIT、GFM 完整、跨块选择、懒加载 |
| Markdown.Avalonia | 备选：老牌但节奏慢、定制能力弱 |
| 官方 `Markdown` 控件 | 功能最好但在 **Avalonia Pro** 商业层 |
| WebView + JS | ❌ 与"轻量"目标冲突（+100MB、启动慢） |

**不选 WYSIWYG**：那需要自己写 Markdown 感知的富文本编辑器，成本是分栏方案的 10 倍。

### 踩坑（详见 pitfalls §C）

滚动同步连踩三个，彼此独立，任何一个没解决都会完全失效：

1. 不能用 `TextView.DocumentHeight` 算比例（只覆盖已构建的可见行）
2. 反向同步不能设 `ScrollViewer.Offset`（会被逻辑滚动源覆盖）
3. 预览的 `ScrollViewer` 要延迟挂接（在 ControlTemplate 里）

### 被推翻的初稿判断

调研文档初稿写「**不要开 PublishAot**」，理由是 Avalonia/Markdig/TextMate 有反射路径。

**实测推翻了它**：AOT 编译成功、9/9 自检通过、0 裁剪告警、exe 34MB。已在文档更正并标注。

这条记录保留的意义：**没有验证过的推断不要写成定论**。
